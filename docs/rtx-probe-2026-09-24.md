# RTX feasibility: isolated intersection queries

**Result: hardware queries were 3.26–3.76× faster on the curved-path replay.**
Random short-segment workloads showed 7.68–13.60×. This warrants a more representative
prototype if we decide to pursue a hardware backend. It is not an FPS forecast, and
the shipping Minecraft renderer still uses OpenGL software intersections.

Measured on 24 September 2026: NVIDIA GeForce RTX 5070 Ti, driver 616.92, Windows,
Java 21, LWJGL 3.3.3, Vulkan 1.2 ray queries. Minecraft was closed normally for the
measurements. No production code or world data changed.

## Query timings

Times below are milliseconds **per 262,144 queries**, measured on the GPU. Each
sample runs 16 serialized dispatches and divides their total by 16; 12 warmup pairs,
30 measured pairs, alternating order. Both paths intersect the same opaque triangles
and receive identical query buffers. Data is warm in GPU caches.

| Synthetic scene | Query set | Software median | RTX median | Speedup | Software / RTX p95 |
|---|---|---:|---:|---:|---:|
| 35,578 triangles | Random 4-block segments | 0.100952 | 0.013142 | 7.68× | 0.115788 / 0.013264 |
| 35,578 triangles | Random 16-block segments | 0.202836 | 0.015306 | 13.25× | 0.238610 / 0.015320 |
| 35,578 triangles | Curved-path replay | 0.038614 | 0.011852 | 3.26× | 0.039122 / 0.011866 |
| 136,468 triangles | Random 4-block segments | 0.102758 | 0.013386 | 7.68× | 0.113800 / 0.013400 |
| 136,468 triangles | Random 16-block segments | 0.218634 | 0.016078 | 13.60× | 0.249354 / 0.016092 |
| 136,468 triangles | Curved-path replay | 0.044622 | 0.011860 | 3.76× | 0.045122 / 0.011960 |

Scenes contain block-column top/step surfaces, 128 actor-sized boxes and 32
cloud-shaped boxes. They are constructed fixtures, not captured Minecraft worlds.
The replay follows CPU-integrated Schwarzschild paths and divides their straight
chords to stay within 16 blocks. Rays continue in the replay even after geometry
would have stopped a real renderer; every chord becomes an independent query.

The replay's hit rate is only about 0.75%; random 4-block queries hit about 6.6–7.2%,
and 16-block queries about 24.0–25.7%. These rates and cache locality materially affect
the result. The curved workload is a closer question than a long straight camera ray,
but it still leaves out important optimizations and costs of our actual renderer.

## Setup and accuracy

| Scene | Software BVH nodes | Hardware BLAS build, GPU | TLAS build, GPU | Hardware AS storage |
|---|---:|---:|---:|---:|
| 35,578 triangles | 12,757 | 0.305 ms | 0.026 ms | 2,208,512 bytes |
| 136,468 triangles | 48,463 | 0.486 ms | 0.024 ms | 8,444,800 bytes |

These are single setup observations, not warmed build distributions. Allocation plus
build wall time was 13.044 ms for the first scene and 3.436 ms for the second, reflecting
different startup/cache conditions; don't infer that the larger scene builds faster.
CPU scene generation plus software tree building took 49.945 and 45.861 ms respectively,
also with Java warmup differences. Native geometry capture and animated rebuilds are absent.

Compared **1,572,864 query results**, plus **768 sampled brute-force double CPU checks**.
There were no unexplained classification disagreements or distance failures. Five
hit/miss differences remained at triangle edges: two on the small curved replay,
three on the larger replay (including the same two). The hardware answer agreed with
the CPU reference in all five. The largest shared-hit distance difference was
0.000002862 blocks. Exact agreement is not claimed.

The edge cases expose sensitivity in this probe's ordinary float Möller–Trumbore
baseline. They are not new confirmed visible bugs in the production shader, which
uses different storage, traversal and compilation. A backend migration must still
test seams, cutout texels, grazing rays and layer ordering. We retained the edge cases
in all timings and recorded them explicitly in the log.

## What the comparison does—and does not—tell us

The software baseline is a compact standalone Vulkan compute BVH, built using the
same broad midpoint/preorder idea as our renderer. It is **not** the current OpenGL
executable. It omits our quad layout, chunk hierarchy and empty-space certificates.
In particular, a real ray can skip many miss queries using those certificates.

Hardware builds its own acceleration structure and uses its own traversal algorithm;
the comparison is between complete intersection approaches, not a controlled
isolation of “RT-core silicon” with the same tree. RT queries also run here without
the large integrator/material program's register pressure. Repeated inputs, relatively
small scenes, opaque geometry and low replay hit rate make this a favorable test.

There is no texture alpha, translucent continuation, native lighting, sky capture,
Glowing pass, moving-geometry update, or OpenGL/Vulkan resource sharing in the timed
work. None of their cost disappears because an intersection query is faster.

**Decision:** retain the production renderer. The next useful RTX experiment, if
prioritized, is actual captured terrain/moving geometry and actual chord logs,
followed by cutout/translucent behavior and resource-sharing overhead. Only then
would a live image-quality/FPS comparison justify a production backend. The original
optical-table and moving-tree reuse ideas remain valid alternatives.
